# 桌面工作台：后端对接需求

本轮把工作台改成任务对话加分层面板，并把算法库、仿真放到第一层。新增接口全部是增量的，没有改动 `services.py`、`simclient.py`、`bridge_runtime.py`、`processes.py`、`fieldsim.py`、`fieldworld.py`、`field_sim_session.py`、`urp_sim_session.py`、`navigation_profile.py`、`lanes.py`。下面是需要这些模块的负责方决定或补充的事项。

## 桌面安装版的影响

- `services.py`、`fieldsim.py` 没有改动。Windows 上的进程控制由 `urp_lab/compat.py` 提供，`/proc` 相关函数在 Windows 上走不到。
- 安装包不含 ROS 文件。`bridge_runtime.verified_bridge()` 要求桥接在运行它的机器上编译并通过指纹，放进安装包后校验不过，所以安装版的 Gazebo 一律走容器后端。如果以后要让 Linux 安装版直接用本机 ROS，需要负责方提供一条在用户机器上构建桥接的路径。
- `solvers/routing.py` 改了一行：JS 基线的 `node` 改用 `paths.node_command()`，桌面应用借此复用 Electron 自身的运行时。
- 安装版没有 `src/backend/.venv` 和 `src/start.sh`。`services.py` 没有改：网关在 `URP_DESKTOP=1` 时把 `start_archive` 指向数据包路径，并改写档案后端这一行的说明和控制按钮（`gateway.installed_rows`）。
- Windows 上 `os.killpg` 一律是 `taskkill /T /F`，因为没有控制台的子进程收不到温和的请求。`stop_archive` 的 SIGINT 就会结束档案后端，它靠 SQLite 自身保证一致性。
- `src/backend/backend/jobs.py` 的 CVRP 进程监督要求 Linux，所以 Windows 上档案后端以 `local_import_query` 模式运行，数值任务页列出算法但不能提交。

## 已接入，不需要改动

| 接口 | 用途 |
|---|---|
| `GET /lab/api/algorithms/stats`、`/algorithms/{id}/history` | 算法库的本机记录，从 `runs` 表只读计算 |
| `GET/POST /lab/api/physics/runs`、`/physics/runs/{id}`、`/physics/runs/{id}/cancel`、`/physics/engines` | MuJoCo 物理运行；进程隔离，结果存 `physics_runs` 表和 `runtime/physics/` |
| `GET /lab/api/agent/capabilities`、`/agent/jobs` | 能力清单和后台任务汇总 |
| `POST /agent/sessions/{id}/control` 的 `simulate` 动作 | 报告之后由用户发起仿真，记为 `user_approved` |
| `fieldworld.build`、`FieldSimManager.state/result/stop` | 只调用，不修改 |

`fieldcheck.py` 的逐车检查抽成 `track_check(plan, result)`，判定逻辑和提示原样保留，这样 Gazebo 和 MuJoCo 用同一份检查。

## 需要决定

1. **非理想执行进入 MuJoCo。** 现在 `execution` 非空（地面分区、合成定位）和各向异性轮胎都直接拒绝，不做近似。地面分区可以用分块摩擦实现，但摩擦组合规则要和 `field_nonideal.ground_collisions` 对齐；合成定位需要把 `field_localization` 的估计器接到 MuJoCo 循环。这两项都要负责方确认语义。
2. **Gazebo 伺服与 MuJoCo 伺服。** Gazebo 的 DiffDrive 直接设定关节速度，MuJoCo 通过力达到速度，增益固定为 `SERVO_KV = 30`（车轮等效惯量下约 9 ms 时间常数）。如果后续改变车辆质量或轮径，这个值要一起复核；门槛是刚体不再出现可见的横滚和俯仰。
3. **多车并行。** 两个引擎都走 `exclusive_mission_v1`，整段任务依次执行。规划工期是各车并行的恒速估计，因此多车时实际工期明显更长。若引入并行避碰，`mujoco_field.execute` 里 `MissionQueue` 要同步替换。
4. **旧记录。** `rigid/3`、`rigid/4`、`rigid/5` 的记录缺少 `actuator_mode` 等参数，不能在 MuJoCo 复现，界面上不会列出对比结果。是否为这些旧模型补写参数由负责方决定；原记录不动。

## 需要补充

0. **停车位检查只查了一个方向（`fieldworld.plan_vehicles`）。** 新车位会和已有车辆的出入通道比较，但新车辆的出入通道没有和已有车位比较：循环里是 `a.distance(Point(c)) for a in approaches`，缺 `approach.distance(Point(s)) for s in spots`。真实复现：90×60 米果园 3 台车，③ 号车从 (1.15, 9.15) 出发时经过 ② 号车位 (1.15, 5.95) 约 0.95 m，低于要求的 1.78 m，Gazebo 触发车间距离保护（1.104 m），MuJoCo 预演在同一位置触发（1.117 m）。这只影响 PyVRP 和 OR-Tools 方案，节约算法方案走得通。harness 已改为优先送通过预演的方案，但根因在这里，建议补上这个方向的检查。证据见 `setup/2026-11-05/desk/sim2sim/`。
1. **`FieldSimManager` 重启后的会话归属。** 网关重启后 `state()` 返回 `idle`，智能体无法判断之前守着的会话是否已结束。希望补一个按 `session_id` 查询结果状态的只读方法，不依赖 `self.meta`。
2. **`results()` 里带上 `check.valid`。** 现在要读完整 `result.json` 才能拿到运行核验，文件较大。
3. **田间仿真进度事件。** 目前靠轮询 `state()`，如果走现有事件总线，对话里的实时进度和后台任务列表都不必再轮询。
