## 审阅后的必要修正

1. 执行预测只适用于内置同构差速仿真模型；显式车队类别、非理想地面、越界速度/半径和车辆数拒绝预测，并保存原因。不能把固定机器人模型套到异构车队。
2. 时间排名在同一候选集合统一口径：全部具备相同非空模型、`estimated` 状态和正有限非布尔预测值才按预测排序，否则整体使用原目标值；结果记录 `ranking_basis`。智能体的比较工具共用同一门槛。前端预测列保留数值展示，但不再标记预测最优；最佳方案卡片显示实际排序口径。不把缺失预测的恒速数字与其他方案的协调预测混排。
3. 附加预测在可终止子进程执行，最多 0.5 秒且只用原求解预算减去 0.25 秒输出余量后的剩余时间，不借用 jobs 的 2 秒收尾余量；求解器原 watchdog 继续生效，外部墙钟预算不放宽。预测失败/超时记录 `unavailable`，不丢弃已有成功求解结果。
4. 冻结 Gazebo 回放按原交通策略运行，同时从原策略派生 `traffic_mode`，避免协调记录被标成串行。
5. 无环性与进展声明限于事件依赖和明确运动假设。有限仿真与车距保护不构成实车安全证明。

已有源码中的科研会话、数据互通、Windows watchdog、应用 ID、可执行名和私有配置兼容性保留。生产 Gazebo 协调控制并未随本候选启用；历史 `gazebo-patch.diff` 与三例实验仍只作历史证据。

## 未完成与协作边界

- 继承自 main 的物理入口仍用统一机器人速度和半径，且不会拒绝显式异构车队；独立审阅已构建两类速度/半径实例并确认其被统一为固定模型。预测入口拒绝异构并不等于物理入口已支持异构，因此本轮不宣称异构实体验收或对该边界作保证。
- `PhysicsManager.submit` 仍在启动后台执行前同步编译协调计划；最大车辆数、长路线和异常密集交会下的编译延迟与资源压力尚未验收。
- 没有进行本轮真实 Gazebo、真实 Windows/WSL、真实设备、完整新安装包或 Docker 镜像发布验收；不把 Linux 上的 Timer 模拟称为 Windows 实测。
- 未做新模型付费调用、用户实际数据迁移、安装/Dock 改名、原目录清理或分支删除；不能以本候选通过为由关闭全部数据恢复与旧客户端迁移事项，独立约 1.72 GB 历史数据缺口仍未由此解决。
- 本报告形成时，`claude/lab-polish` 按当时要求保留；其后用户已将目标调整为只推进 `main`，该保留例外不再适用。当前约定以 `AGENTS.md` 和 `docs/current-index.md` 为准。任何清理仍须重新核对分支头、成果保全和运行依赖；本次整合没有覆盖该工作区，也没有操作其他人的可写运行数据。
